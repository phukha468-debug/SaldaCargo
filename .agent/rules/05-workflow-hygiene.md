# 05. Процесс разработки, Гигиена контекста и База знаний

## 1. Plan First (Обязательный план перед кодом)

> **Критическое правило:** Для любой нетривиальной задачи (новая фича, изменение схемы БД, рефакторинг, работа с безопасностью или API) **сначала** формируется **Implementation Plan**:
>
> 1. Список затрагиваемых файлов и модулей.
> 2. Проверка соответствия безопасности (RLS, `organization_id`, RBAC, Zod) и модульности (Feature Flags).
> 3. Риски и план отката (rollback).
>
> **Внесение изменений в код начинается ТОЛЬКО после явного подтверждения плана пользователем.**

## 2. Минимальный дифф и запрет самодеятельности (Zero Bloat)

- Изменять код **строго в пределах текущей задачи**. Не переформатировать и не рефакторить соседний несвязанный код.
- Не добавлять новые npm-зависимости без согласования.
- Если в коде найдены две версии одной функциональности — **остановиться и спросить пользователя**, какую оставить.
- Перед завершением задачи проверять `git diff`, `pnpm turbo typecheck`, `pnpm test` и `lint`.
- **Обязательное тестовое покрытие:** любая новая бизнес-логика (финансы, ЗП, авторизация, безопасность, сервисный слой `packages/service`, `packages/shared`, `packages/payroll`) **обязательно** сопровождается unit-тестами Vitest. Запуск `pnpm test` перед сдачей задачи обязателен — все тесты должны проходить без ошибок.

## 3. Экономия контекста (Context Hygiene)

- **Точечное чтение:** запрещено читать большие файлы целиком. Использовать поиск и чтение целевых диапазонов строк (`StartLine` / `EndLine`).
- **Лаконичный вывод:** не выводить в чат длинные логи терминала и сырые JSON-дампы — только краткую суть и статус.
- **Проактивный `/compact`:** после завершения крупного этапа работы явно предлагать пользователю выполнить `/compact` или открыть новый чат.

## 4. Регламент миграций БД

1. Сверять текущую схему по `kb/wiki/Справочник_таблиц_БД.md` и `supabase/migrations/`.
2. Имя файла строго с 14-значным timestamp: `supabase/migrations/YYYYMMDDHHMMSS_<description>.sql`.
3. В начале файла указывать комментарием план отката (rollback).
4. Миграции содержат **только чистый DDL** (никаких фамилий сотрудников и данных конкретного клиента).
5. После миграции обновить типы БД (`packages/types/src/database.types.ts`) и `kb/wiki/Справочник_таблиц_БД.md` в том же коммите.
