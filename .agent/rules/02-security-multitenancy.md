# 02. Безопасность, Multi-tenancy и RBAC

## 1. Изоляция данных (Multi-tenancy & Strict RLS)

- Каждая доменная таблица в целевой PRO-схеме обязана иметь `organization_id UUID NOT NULL REFERENCES organizations(id)`.
- **RLS обязателен на 100% таблиц.** Категорически запрещено создавать политики `USING (true)` / `WITH CHECK (true)` для `PUBLIC` или `anon`, а также выдавать `GRANT ALL TO anon`.
- **Старое правило «всегда использовать `createAdminClient()` в обход RLS» — ОТМЕНЕНО для пользовательских API.**
  - Пользовательские запросы обязаны выполняться в контексте авторизованного пользователя (JWT с `org_id` и `roles`) под защитой RLS.
  - `createAdminClient()` (`SUPABASE_SERVICE_ROLE_KEY`) допустим **исключительно** в системных cron-задачах, вебхуках и фоновых воркерах с обязательной явной фильтрацией `WHERE organization_id = $orgId`.

## 2. Аутентификация и RBAC

- **Запрещены** неподписанные cookies с сырым `user.id`, plaintext-сравнение PIN-кодов и эндпоинты вроде `/api/auth/session`, принимающие произвольный `user_id` без криптографической проверки.
- Авторизация MAX MiniApp обязана валидировать HMAC-подпись `initData`.
- **Каждый API-роут** обязан проходить через единый guard (`withAuth` / `createApiHandler`), проверяющий:
  1. Валидную подписанную сессию / JWT.
  2. Принадлежность к организации (`organization_id`) и статус подписки.
  3. Включённый бизнес-модуль (Feature Flag).
  4. Гранулярное право доступа (**Permission-based RBAC**, например `finance.transfer`, `trips.review`, `garage.manage`, `users.manage`).
- Никогда не брать `user_id` или `organization_id` из query-параметров / body для определения прав (защита от IDOR).

## 3. Валидация входных данных и защита от инъекций

- **100% API-роутов**, принимающих body или query-параметры, обязаны валидировать входные данные через **Zod-схемы** (никакого сырого `await req.json()` без парсинга).
- **Запрещена** прямая интерполяция пользовательского ввода в PostgREST `.or()` / `.filter()` без экранирования спецсимволов (`,`, `.`, `(`, `)`).
- Все загрузки файлов обязаны проверять авторизацию, MIME-тип, максимальный размер и санитизировать путь в Storage (с префиксом `organization_id/`).

## 4. Секреты, TLS, Cron и Observability

- **Категорически запрещено** хранить API-ключи, токены, пароли, PIN-коды и URL с ключами в исходном коде, скриптах деплоя, миграциях и локальных конфигах агентов (`.claude/settings.local.json` должен быть в `.gitignore`).
- Секреты клиентов (Wialon, банк, топливные карты, боты) хранятся в БД только в зашифрованном виде (`organization_integrations`).
- Все `/api/cron/*` обязаны проверять `CRON_SECRET`; вебхуки — обязательную проверку подписи/секрета.
- **Запрещено** использовать `rejectUnauthorized: false` на HTTPS-запросах (для банков РФ подключать корневой сертификат Минцифры).
- Ошибки внешних API и кронов нельзя тихо проглатывать: логировать структурированно (без утечки PII/токенов) с указанием `requestId` и `organizationId`.
