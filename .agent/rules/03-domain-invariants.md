# 03. Доменные и финансовые инварианты (НЕ НАРУШАТЬ)

Эти бизнес-правила проверены в реальной эксплуатации и **обязаны сохраняться без потерь** при любом рефакторинге и переходе на PRO-архитектуру.

## 1. Двухосный статус транзакций

У каждой финансовой транзакции два независимых статуса:

- `lifecycle_status`: `draft → approved → cancelled` (факт утверждения руководством).
- `settlement_status`: `pending → completed` (факт движения денег).

**Инвариант:** Балансы кошельков, подотчёты и P&L считаются **ТОЛЬКО** по записям с `lifecycle_status = 'approved' AND settlement_status = 'completed'`.  
Сотрудники создают записи в статусе `draft`; администратор переводит их в `approved`. Прямые транзакции администратора создаются сразу `approved + completed`.

## 2. Динамический расчёт балансов

- Баланс любого кошелька (сейф, расчётный счёт, топливная карта, топливный куб, гараж) и подотчётного остатка водителя **вычисляется на лету из журнала транзакций**.
- **Запрещено** хранить текущий баланс как статическое редактируемое поле таблицы (коррекция остатка всегда оформляется транзакцией коррекции).

## 3. Деньги — только строкой (`DECIMAL(12,2)`)

- В PostgreSQL денежные суммы хранятся исключительно в `DECIMAL(12,2)`.
- В TypeScript/API денежные суммы передаются **строкой** с двумя знаками (`"5000.00"`), никогда не `float`. Для отображения используется компонент `<Money />` из `@saldacargo/ui`.

## 4. Зарплата водителя — строго ручной ввод

- ЗП водителя (`trip_orders.driver_pay`) вводится и корректируется **вручную**.
- Система может показывать расчётную подсказку (~30%), но **категорически запрещено** писать автоматический пересчёт или БД-триггеры, перезаписывающие введённую пользователем сумму.

## 5. Soft-delete вместо физического `DELETE`

- Для всех бизнес-сущностей (рейсы, заявки, транзакции, заказ-наряды, контрагенты) запрещён физический `DELETE`.
- Отмена выполняется через `lifecycle_status = 'cancelled'` с заполнением `cancelled_reason`.
- Единственное техническое исключение: `trip_expenses` (допустимо физическое удаление до утверждения рейса).

## 6. Идемпотентность мутаций

- Каждая форма создания сущности генерирует `idempotency_key = crypto.randomUUID()` при монтировании.
- При повторной отправке (код ошибки PostgreSQL `23505`) сервер обязан вернуть существующую запись со статусом `200`, а не создавать дубль.

## 7. Роли пользователей (`users.roles`)

- Поле `roles` — это **массив** (пользователь может совмещать роли).
- Фильтрация в Supabase выполняется строго через `.contains('roles', ['driver'])`, никогда `.eq('role', ...)`.

## 8. Критические кросс-инварианты рейсов и дебиторки

1. **Апрув рейса:** одновременно переводит `trips.lifecycle_status = 'approved'` И все его `trip_orders.lifecycle_status = 'approved'`.
2. **Возврат рейса на доработку:** переводит `trips.lifecycle_status = 'returned'`, откатывает `trip_orders.lifecycle_status = 'draft'` и очищает итоговый одометр.
3. **Синхронность ревью:** рейсы со статусом `completed` и `lifecycle_status IN ('draft', 'returned')` синхронно отображаются и в разделе `/review`, и в папке «На ревью» конвейера заявок.
4. **Погашение дебиторки:** одновременно переводит `settlement_status = 'completed'` И создаёт `income`-транзакцию в журнале.
5. **Отменённые рейсы:** во всех списках и расчётах водителя всегда фильтровать `neq('lifecycle_status', 'cancelled')`.
